# Запуск и испытания прототипа

## Подготовка

Используйте тестовый рабочий стол Windows 11 x64 и тестовый каталог для фрагментов. Скачайте нативный MediaMTX v1.21.3 и проверьте архив по `checksums.sha256`. На агенте подготовьте GStreamer 1.28.7 MSVC x64 с `d3d11screencapturesrc`, `x264enc`, `h264parse`, `whipclientsink` и, при проверке Media Foundation, `mfh264enc`. Укажите путь к папке с `gst-launch-1.0.exe` и `gst-inspect-1.0.exe`. Для сборки процессов контроля захвата и пробы ввода нужен .NET SDK 11. [Релиз MediaMTX](https://github.com/bluenviron/mediamtx/releases/tag/v1.21.3), [сборки GStreamer](https://gstreamer.freedesktop.org/pkg/windows/1.28.7/).

## Локальная проверка DXGI

Команды запускают кодирование кадров в активном локальном сеансе и считают их в памяти. Для этой проверки сервер MediaMTX и пароль не нужны. Повторите команду с `-Encoder MediaFoundation` для аппаратного кодирования.

```powershell
dotnet build .\agent\Ekravio.Capture -c Release
.\agent\Ekravio.Capture\Start-Prototype.ps1 -GStreamerBin 'C:\lab\gstreamer\bin' -ProbeOnly -DurationSeconds 5
```

Ожидаемый результат — 50 кадров H.264. Если GStreamer согласовал параметры потока, а число кадров равно нулю, повторите пробу из видимого терминала на разблокированном тестовом ПК. Включите сообщения DXGI командой `$env:GST_DEBUG = 'd3d11screencapturesrc:2'`.

## Сервер, захват и архив

Сгенерируйте два разных случайных пароля длиной от 16 символов. Для издателя используйте латинские буквы, цифры, `_` или `-`. Введите их в запросах скриптов. Скрипт сервера сохраняет SHA-256 паролей внутри сгенерированной конфигурации.

Из корня репозитория запустите нативный MediaMTX в первом терминале. Для каждого нового запуска с другими параметрами указывайте свободный `-RunDirectory`.

```powershell
.\deploy\mediamtx\Start-Prototype.ps1 -MediaMtx 'C:\lab\mediamtx.exe' -RunDirectory '.stage0\run-01'
```

Для раздельных ПК укажите `-BindAddress`, `-ServerName`, `-Certificate` и `-CertificateKey`. Используйте доверенный агентом и браузером PEM-сертификат для `ServerName`. Разрешите TCP 8889, TCP 9996 и UDP 8189 только в области тестовой сети. Для нативного Linux запустите тот же скрипт с `pwsh` и бинарником MediaMTX для Linux. Это стендовый запуск в терминале.

Во втором видимом терминале Windows запустите захват. Для удалённого сервера добавьте `-WhipEndpoint https://имя-сервера:8889/stage0/whip`. Испытайте `-Encoder MediaFoundation` отдельным запуском. Введите `START` только на экране, предназначенном для испытания. По умолчанию прогон рассчитан примерно на 75 секунд, `Ctrl+C` завершает его вручную.

```powershell
.\agent\Ekravio.Capture\Start-Prototype.ps1 -GStreamerBin 'C:\lab\gstreamer\bin'
```

1. В браузере откройте выведенный сервером адрес `Live`. Введите имя `viewer` и пароль чтения. Проверьте, что движение на тестовом рабочем столе появляется на странице.
2. Закройте браузер и повторите прогон. Откройте выведенный адрес `Archive` и найдите диапазон в JSON. Откройте его `url`. Проверьте длительность и воспроизведение. Сегменты находятся в `recordings/stage0` под каталогом запуска.
3. На тестовом ПК во время захвата заблокируйте сеанс или переключитесь на другого пользователя. Проверьте завершение GStreamer. После возвращения в исходный сеанс для новой трансляции повторите запуск и подтверждение `START`. Для смены разрешения и потери сети сделайте отдельные прогоны.

Автоматический тест медиатракта передаёт синтетический поток при закрытом браузере, запрашивает список диапазонов, скачивает MP4 и проверяет число декодированных кадров. Для теста нужен `avdec_h264` из `gst-libav`. Тест также проверяет отказ анонимному клиенту и запрет чтения архива под учётной записью издателя.

```powershell
.\tests\windows\Test-MediaPrototype.ps1 -MediaMtx 'C:\lab\mediamtx.exe' -GStreamerBin 'C:\lab\gstreamer\bin'
dotnet run --project .\tests\windows\Ekravio.Capture.Tests -c Release
```

## Активность ввода

```powershell
dotnet run --project .\agent\Ekravio.SessionMonitor -c Release -- 90 60
dotnet run --project .\tests\windows\Ekravio.ActivityProbe.Tests -c Release
```

1. Запустите пробу в тестовом интерактивном сеансе. Проверьте вывод `input_seen` при движении мыши, клике, прокрутке и наборе тестового текста. Сделайте паузу дольше порога, проверьте переход в `idle`. Первая секунда служит базовой точкой.
2. Повторите в отдельном RDP-сеансе, включая подключение без ввода. Проверьте `session_transport=rdp`. Отсоединитесь и подключитесь повторно, проверьте пропуск и отсутствие ложного ввода от подключения.
3. Повторите в AnyDesk, TeamViewer, RustDesk и RuDesktop. Укажите версию, режим установки, ОС и права. Поле `session_transport` описывает тип Windows-сеанса. Для сеанса Windows Console выводится `console`, в том числе при вводе через AnyDesk. Все испытания повторяются при остановленном захвате.
